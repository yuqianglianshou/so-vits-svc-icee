# 发布稳定化设计

## 1. 背景

当前项目基于 so-vits-svc 4.1 进行二次开发，已经形成以可视化训练页、推理页、单模型工作区和依赖管理为核心的稳定使用路径。项目准备对外发布，但 README、文档导航、GitHub 协作入口和自动化检查仍保留部分上游内容或缺少发布级保障。

本轮工作的目标不是升级模型或重写工程，而是在冻结模型行为的前提下，提高首次使用成功率、故障信息质量、文档一致性和发布可验证性。

## 2. 目标

本轮交付应达到以下结果：

1. 新用户只阅读项目首页即可理解项目定位、与原版的差异、支持范围和最短使用路径。
2. 中文 README、英文 README 和 docs 导航中的关键事实保持一致。
3. 文档不存在仓库内死链，不再把用户错误引导到上游仓库或旧版目录。
4. GitHub Issue 模板能够收集当前项目所需的环境、版本、复现步骤和日志。
5. 在不下载模型、不要求 CUDA 的环境中，可以执行完整的发布前静态检查。
6. 现有训练、推理、模型格式、目录布局和默认参数保持不变。

## 3. 非目标

本轮明确不包含：

- 更换 ContentVec、RMVPE、NSF-HiFiGAN 或扩散模型。
- 修改 loss、网络结构、训练参数或推理参数默认值。
- 启用 AMP、`torch.compile` 或其他训练性能开关。
- 重构 `src/app_train.py`、`src/app_infer.py` 或任务系统。
- 改变模型工作区、依赖资产或 checkpoint 的目录与文件格式。
- 删除旧模型兼容代码。
- 引入新的生产运行依赖。
- 承诺未经实际验证的平台、显卡或训练速度。

## 4. 发布定位与支持边界

项目首页应将项目定位为：

> 面向本地离线使用的 So-VITS-SVC 可视化训练与高质量歌声转换工作台。

本次发布重点支持：

- Windows 10/11 64 位。
- NVIDIA GPU 和 CUDA 环境。
- Python 3.11。
- 单说话人、单模型工作区训练路线。
- `python -m src.app_train` 和 `python -m src.app_infer` 两个主入口。

以下内容必须标记为限制或非主线：

- Linux 仅作为理论兼容环境，除非完成实际验证。
- macOS 不作为正式训练平台。
- 多说话人、实时转换和 ONNX 不作为当前发布的主流程承诺。
- 浅扩散、特征检索和增强器按实际界面行为说明必需性，不夸大质量收益。

- 故障排查。

## 7. GitHub 项目入口

### 7.1 Issue 模板

现有 Issue 模板中的上游链接、旧分支选项、旧目录和攻击性措辞全部移除。保留三类入口：

- Bug 报告。
- 安装与使用帮助。
- 功能建议。

Bug 和帮助模板至少收集：

- 项目版本或 commit。
- 操作系统。
- GPU 与显存。
- Python、PyTorch 和 CUDA 版本。
- 使用的应用入口或操作步骤。
- 模型工作区状态。
- 可复现步骤。
- 预期行为和实际行为。
- 完整日志。
- 是否稳定复现。

`config.yml` 中的讨论链接必须指向当前仓库；若当前仓库未启用 Discussions，则改用 Issue 引导，不保留无效链接。

### 7.2 贡献与变更记录

新增：

- `CHANGELOG.md`：说明当前发布相对上游的主要变化、兼容性和限制。
- `CONTRIBUTING.md`：说明环境、分支、检查命令、Issue 和 PR 要求。
- `.github/PULL_REQUEST_TEMPLATE.md`：要求说明范围、验证方法、兼容性影响和文档更新。

## 8. 自动化检查设计

### 8.1 发布检查脚本

新增 `scripts/check_release.py`，只使用 Python 标准库，执行以下检查：

1. README 和 docs 中的仓库内相对链接目标存在。
2. 两个应用入口、配置模板和关键启动脚本存在。
3. JSON 和 YAML 配置模板可解析；YAML 检查复用项目已有 PyYAML，不把它作为脚本启动前的隐式假设，缺少依赖时给出明确提示。
4. README 中列出的主入口与实际入口一致。
5. 文档中不再出现已废弃的仓库内路径和上游 Issue/Discussions 链接。
6. Git 跟踪文件中不包含模型权重、生成音频、日志、虚拟环境或缓存文件。

检查失败时输出具体文件、问题和修复方向，并以非零状态退出。

### 8.2 最小单元测试

新增 `tests/`，优先覆盖不依赖 CUDA 和模型权重的稳定接口：

- 工作区名称和路径解析。
- 模型目录状态识别。
- 配置模板读取与 batch size 同步。
- 模型依赖状态判断。
- 数据集目录识别。
- 推理输出路径生成。

测试不得修改真实 `model_assets/workspaces`；使用 pytest 临时目录或标准库临时目录隔离文件系统。

### 8.3 CI

CI 使用 Python 3.11，拆分为：

- `lint`：显式安装固定版本 Ruff 并运行 `ruff check src scripts tests`。
- `static-smoke`：运行 `compileall` 和现有两个 smoke 脚本。
- `release-check`：运行发布检查脚本和不依赖模型的单元测试。

CI 不安装 CUDA、不下载模型权重、不执行正式训练或推理。工作流只检查，不自动修改 PR 内容。

## 9. 启动脚本与错误信息

三个 Windows 启动脚本保留现有启动行为，仅允许增加：

- 当前 Python 路径和版本提示。
- 缺少虚拟环境时指向统一安装文档。
- 子进程异常退出时显示退出码。
- 训练任务和推理输出的日志位置提示。

不得在启动脚本中自动创建环境、安装依赖、下载模型或更改系统配置。

与文档整理直接相关的错误提示可以改进，但不得改变自动回退、checkpoint 恢复或训练状态机行为。发现高风险缺陷时记录到已知限制或后续工程重构清单。

## 10. 数据流和兼容性

本轮不改变运行时数据流：

```text
用户 -> 启动脚本/模块入口 -> Gradio 页面 -> 现有任务与模型逻辑
```

新增的发布检查位于运行时之外：

```text
维护者/CI -> 发布检查脚本 -> 文档、配置、路径和 Git 跟踪状态报告
```

因此现有模型工作区、checkpoint、训练特征包和推理包不需要迁移。

## 11. 错误处理原则

- 用户文档给出可执行的恢复步骤，不只描述错误。
- 启动脚本错误包含实际使用的 Python 路径和退出码。
- 发布检查列出所有可检测问题，而不是发现第一个问题后立即停止。
- CI 输出必须能定位到文件和检查项。
- 不通过捕获异常并静默忽略来换取“检查通过”。

## 12. 实施顺序

1. 重写 README 和 docs 导航，修复死链。
2. 新增快速开始、兼容性、资产清单、限制和发布检查文档。
3. 更新 Issue、PR、贡献和 Changelog 入口。
4. 实现发布检查脚本及其测试。
5. 增加最小业务单元测试。
6. 更新 CI。
7. 统一 Windows 启动脚本提示。
8. 执行完整静态验证。
9. 在干净 Windows 环境执行人工发布验收，并记录实际验证结果。

人工 Windows 验收依赖真实 NVIDIA 环境，不由无 GPU 的 CI 代替；在人工验收完成前只能标记为 Release Candidate。

## 13. 验收标准

发布候选必须满足：

- 中文和英文 README 的关键事实一致。
- 仓库内 Markdown 链接检查通过。
- README 可以直接引导新用户完成安装、启动和找到训练/推理流程。
- Issue 模板不再引用上游仓库、旧分支或旧目录。
- CI 不需要 CUDA 或模型权重即可通过。
- `compileall`、现有 smoke 检查、发布检查和新增单元测试全部通过。
- 未修改模型结构、默认训练参数、checkpoint 格式和工作区布局。
- Git 未跟踪模型权重、生成音频、训练日志、虚拟环境或缓存。
- Windows 人工验收记录包含实际系统、GPU、Python、PyTorch 和 CUDA 版本。

## 14. 发布后工程重构入口

本轮发现但不处理的结构问题统一进入后续工程重构：

- 拆分训练和推理应用入口。
- 统一任务运行器和结构化状态。
- 定义编码器、F0、声码器与模型包契约。
- 收敛宽泛异常和静默回退。
- 清理第三方代码与项目自有代码边界。
- 建立模型质量评测与性能基准。

发布稳定化完成后，再为上述内容分别建立设计和实施计划，不与本轮混合。
